SANDBOXED BY DEFAULT · AUDIT FIRST · HUMAN GATED

AI agents that execute real code.
On machines that never mattered.

PRE Secure is a hardened agentic AI platform built around one question: can we give people agents that actually run code and take actions — without handing a probabilistic system deterministic power over real infrastructure?

The answer: agents never touch the host. Every command runs inside a disposable, hardware-isolated Firecracker microVM. The worst thing an agent can do is destroy a sandbox that never mattered.

01 · THE PROBLEM

The failure is architectural, not a model-quality problem

AI agents are extraordinarily useful — and extraordinarily dangerous when they execute code directly on real machines. Coding agents have caused real, headline-making incidents by doing exactly what they were asked to do, on the wrong target, with no containment between "the agent's workspace" and "everything else."

Better prompting doesn't fix a system where the agent's shell is the production shell. The fix is to make that untrue:

Agents should never have execution access to anything that matters, by default. They get a disposable machine. If they misuse it, you throw the machine away and read the log of what happened.

That's the entire thesis. Everything on this page is the engineering that makes it true in code — not just true on a slide.

✕
Typical agent harness
agent shell = your shell. One confused tool call away from rm -rf on the wrong box.
✓
PRE Secure
agent shell = a microVM with its own kernel. Blast radius: one disposable sandbox.
PRE Secure decides what the agent does. AgentENV decides where it can do it.

Two independent systems, deliberately decoupled. Swap the agent framework — the isolation survives. Swap the sandbox provider — the agent never notices (the API is E2B-compatible, the de facto standard).

The sandbox lifecycle — persistent, pausable, disposable

    
Each user gets one persistent sandbox, not a fresh one per command — agent work is a sequence (install, write, run, fix, run again), and state should survive it. Idle sandboxes are paused, not destroyed: disk state persists while CPU and memory are freed.

Why not just a sudo rule?
A sudo grant — even a narrow one — is a privilege-escalation path sitting inside the app process, waiting for a supply-chain bug to use it. Instead, the app can only write a file describing a job. A completely separate account, with no sudo and no shared privileges, picks it up. There is no mechanism for the app to force execution.

    
What "approval" actually gates
request_real_action is a distinct tool from bash — the model must consciously choose the exception. Calling it never executes anything; it files a request, fires a real-time toast to admins, and waits.

    
The gate is human-vs-AI, not human-vs-human
An admin may approve their own agent's request — the point is that the AI can never act unilaterally. Self-approvals are flagged selfApproved: true in the audit trail, so the pattern stays reviewable.

07 · AUDIT & TRACEABILITY

    
Four independent trails — and an off-host export for all of them

  

  

    
🛡️
Central security log
Every security-relevant app event — logins, lockouts, role changes, config changes, approvals, exports — logged with actor + IP, and mirrored to the root-owned system journal. If the file and the journal ever diverge, that's a tamper signal.
audit/admin-audit.log

    
📦
Sandbox exec log
Every command an agent runs, per user: identity, sandbox, the command itself, duration, outcome. The answer to "what did the AI do inside its sandbox?"
<user>/aenv-audit.log

    
🚪
Real-action lifecycle log
Every proposed real-host action, end to end: created → approved/denied → enqueued → result. The answer to "what did a human authorize the AI to do outside it?"
<team>/real-action-audit.log

    
🌿
Host config history
Every change to /etc — nginx, systemd units, sudoers — is a git commit with a diff, via etckeeper. The answer to "what changed about the infrastructure itself?"
cd /etc && git log

    
📡
SIEM export API
All application trails, pullable off-host with zero shell access: a read-only API merges them into one checkpointable stream plus a security-metrics snapshot. Per-consumer tokens are issued and revoked from the admin console — shown once, stored only as hashes, last use visible, and their lifecycle is itself audited.
GET /api/siem/audit?since=…

  







  

    
08 · DATA PROTECTION

    
PII is scrubbed where data becomes durable — not where it's useful

    
The agent needs live PII to do its job. The control point is the persistence boundary: the moment data would become long-term, team-shared, or model-bound, it's deterministically scrubbed. Watch it happen:

  

  

    

      
live session → team memory (crossing the boundary)

      

    

    

      
Two tiers: deterministic, then NER
Tier 1 is regex + checksums: Luhn for cards, ISO 13616 mod-97 for IBANs — a compliance control you can demonstrate, covered by tests on every recognizer's positive and negative cases. Tier 2 adds NER for names and locations via a Presidio sidecar bound to loopback only — CPU-fast (~13 ms per paragraph), same placeholder scheme, fail-open with a circuit breaker or fail-closed by config.

      
Typed, stable, non-reversible
The placeholder suffix is a truncated HMAC-SHA256 keyed by the secrets key — the same value maps to the same placeholder in every store (cross-references survive), but without the key it can't be dictionary-reversed.

      
Secrets at rest
Every credential file — OAuth tokens, provider API keys — is AES-256-GCM encrypted, with the key stored outside the data root. A copied data directory alone is ciphertext. Session tokens live in the DB only as SHA-256 hashes.

    

  







  

    
09 · SECURE MODEL INFRASTRUCTURE

    
The model never leaves the building. Neither does your data.

    
Most agent platforms are a thin shell around a third-party AI vendor's API — every prompt, every file, every secret in context crosses the internet to someone else's datacenter. PRE Secure is architected so that inference is infrastructure you control.

  


  

    
  


  

    
Per-team model choice, zero re-architecture
Model serving resolves through a generic OpenAI-compatible provider abstraction. A team can point at fully-local Ollama or an internal vLLM endpoint — the isolation and audit architecture doesn't know or care which model answers.

    
Decoupled by design
Because inference is decoupled from isolation, upgrading models (or adding GPUs) never touches the security architecture — and hardening the security never blocks a model upgrade.

    
The residency guarantee in one sentence
Whether inference runs on-box or on an internal endpoint, no chat, code, context, or credential ever transits a third-party AI vendor. Data residency isn't a policy promise — it's a property of the network topology.

11 · HONEST TRADEOFFS

    
A security document that lists no gaps isn't trustworthy

    
These are real, current, and tracked — stated plainly, the same way the closed ones were before they were closed.

  

  

    
open
The sandbox orchestrator is young. AgentENV is pre-1.0 and ships no auth of its own. Mitigated by strict localhost-only binding and by maintaining a privately patched fork — which helps, but doesn't eliminate the maturity risk.

    
open
Web egress allowlisting shipped — DNS and UDP residuals remain. Sandboxes can now run deny-by-default with a per-user domain allowlist, enforced by a TCP egress proxy built into the maintained fork: web traffic is transparently redirected inside the sandbox's network namespace, matched by HTTP Host / TLS SNI, and resolved host-side so a forged SNI can't pick the upstream address. Access is a per-user admin setting in the UI. Stated plainly, what remains: UDP (QUIC) is not proxied, DNS stays reachable as a low-bandwidth exfiltration channel, and non-web ports are governed by IP/CIDR rules only.

    
open
Street-number address lines are only partially caught. Tier-2 NER (a loopback-only Presidio sidecar) now scrubs names and named locations at every persistence boundary — but bare numeric street lines ("123 Main St") evade general NER; a dedicated address-pattern recognizer is the tracked follow-up.

    
open
Single-box pilot. App, orchestrator, model serving, and proxy share one server — a single point of failure by design, for pilot simplicity. Scale-out is the documented path if the pilot grows.

    
open
SIEM integration is pull, not push. A security team can now export every audit trail off-host through a read-only, token-authenticated API (all three trails merged into one checkpointable stream, plus an operational-metrics snapshot). Credentials are issued per consumer from the admin console — plaintext shown exactly once, only hashes stored server-side, last use visible, each token individually revocable, and both token lifecycle and failed auth attempts are themselves audited. What remains open: nothing pushes — off-host retention cadence depends on the poller, and the file-based trails on the host are still the system of record.
